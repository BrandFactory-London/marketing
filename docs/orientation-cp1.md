## 3. Open questions

- **Q1, sessions and the refresh token.** Lean: **Auth.js v5 with database sessions**, as the handoff suggests.
  - *Version.* `next-auth@5.0.0-beta.32` is the current v5 (still tagged beta; `latest` is 4.24.15). Pin it exactly, with `@auth/drizzle-adapter@1.11.3`.
  - *Allowlist.* The `signIn` callback allows only `profile.email_verified === true` and an email equal to `ALLOWED_EMAIL` (case-insensitive). This callback runs before Auth.js creates a user, so a refused account writes nothing to the database. Refused users land on `/signin?error=AccessDenied`.
  - *Scopes.* `openid email profile https://www.googleapis.com/auth/drive.readonly`, with `access_type=offline` and `prompt=consent`, so Google issues a refresh token on every sign-in. One operator makes the extra consent screen acceptable.
  - *Keeping the refresh token out of plain text.* As noted in the handoff, the Drizzle adapter's `linkAccount` writes `refresh_token`, `access_token` and `id_token` to `accounts` in plain text. I will wrap the adapter: our `linkAccount` removes those three fields before calling the original, so they are always null in `accounts`. Separately, `events.signIn` (which runs on every sign-in, not only the first) encrypts the refresh token and upserts it into `google_tokens`. The columns stay in `accounts` because the adapter expects them. A unit test proves the wrapper strips the tokens; at smoke an independent query proves `accounts.refresh_token IS NULL` and `google_tokens` holds ciphertext.
  - *Refreshing.* `google_tokens` also stores the access token (encrypted) and its expiry. `getGoogleAccessToken(userId)` returns it if it has more than 60 seconds left, otherwise exchanges the refresh token at Google's token endpoint and stores the new one. If Google returns `invalid_grant` (revoked), the function throws a typed error and the caller asks you to sign in again.
  - *Why not JWT sessions.* JWT would put the tokens in a cookie or need the same table anyway, and sessions could not be revoked from the database. Database sessions also make Q2 simple.

Smaller decisions I will take unless you object:
- `APP_ENCRYPTION_KEY` is 32 random bytes, base64. Ciphertext format `v1.<iv>.<tag>.<ciphertext>` (base64url), 12-byte random IV, with associated data naming the purpose and owner (for example `google-refresh-token:<userId>`), so a ciphertext copied into another row will not decrypt. The version prefix allows key rotation later.
- `app_settings` is a single row (fixed id with a check constraint), three text columns defaulting to `claude-opus-5-5`. Values are validated against `src/config/models.ts` in the app, not by a database enum (decision 13 says plain strings). The row is created on first read with `ON CONFLICT DO NOTHING`, which avoids a hand-written seed migration.
- No `verification_tokens` table: it is only used by email sign-in, which we do not have.
- The prototype's brand mark hardcodes `#0e7c86` and `#ffa585`. I will use `var(--brand)` and `var(--aurora-peach)` instead (D.3.2). Note the README reserves aurora colours for generating surfaces; the prototype uses peach in the logo anyway, so I am following the prototype.
