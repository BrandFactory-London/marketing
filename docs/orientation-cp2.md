- **Q5, migration shape and the transactional route.**
  - *New tables (one migration, `0001`):*
    - `clients`: `id` uuid, `name` (required), `main_contact`, `email`, `phone` (optional, per the CRM prototype), `created_at`, `updated_at`.
    - `projects`: `id` uuid, `client_id` (FK, restrict), `name`, `site_url`, `package`, `status`, `status_changed_at`, `publishing_target` (text, check `wix_blog` only for now), `drive_folder_id`, `drive_folder_name`, `drive_folder_checked_at`, `sitemap_imported_at`, `created_at`, `updated_at`. Wix credentials are γ6 columns or a γ6 table.
    - `knowledge_versions`: `id` uuid, `tier` (`agency`, `client`, `project`), `client_id` (FK, nullable), `project_id` (FK, nullable), `version` int, `sections` jsonb (section key to Markdown text), `created_at`. A check constraint ties the tier to exactly the right owner column (agency: neither; client: `client_id` only; project: `project_id` only). A unique constraint on `(tier, client_id, project_id, version)` with `NULLS NOT DISTINCT` (Postgres 15 and later; Neon runs 18, local 16), so two saves cannot both become version N. Later checkpoints point at a version by its `id`.
    - `site_pages`: `id` uuid, `project_id` (FK, cascade), `url`, `path`, `title`, `lastmod`, `imported_at`, unique `(project_id, url)`.
  - *No deletes in γ2.* Clients and projects can be created and edited, not deleted (hard to reverse, and later posts will reference them). Say if you want delete.
  - *How backlog item 6 is proven before 0001 touches the Neon dev branch:*
    1. **Local, through the real driver.** The test starts a small WebSocket-to-TCP relay (the `ws` package) in front of a scratch local database, and points `@neondatabase/serverless` at it (`neonConfig.wsProxy`, plain `ws://`). The real Drizzle `neon-serverless` migrator then runs over it. Tests: applies `0000` and `0001` to an empty database and prints the tables; a second run is a no-op; **atomicity**: a fixture migrations folder whose second migration fails halfway leaves no table from that migration and no migration row (and, because Drizzle runs all pending migrations in one transaction, the first pending one is rolled back too); the guard and target tests stay.
    2. **Neon dev, read-only.** `pnpm db:migrate --remote --check-only` over the new driver, output pasted: expect the five γ1 tables and one migration row.
    3. **Neon dev, rollback rehearsal (needs your go-ahead).** Run the `0001` SQL inside `BEGIN` ... `ROLLBACK` over the WebSocket driver, then the check again: expect the four new tables to have existed inside the transaction and the table list afterwards to be unchanged. This proves transactional DDL on Neon itself, not only locally.
    4. **Then the real migration (needs your go-ahead)**, `pnpm db:migrate --remote`, then your independent SQL check in the Neon SQL editor.
  - The app's runtime driver stays node-postgres (Vercel reaches Neon on 5432). Only the migration script changes.
